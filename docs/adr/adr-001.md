# Architectural Decisions

## Project
Paywall Link Platform

## Purpose

This document defines the core architectural decisions for the MVP system.

These decisions ensure:

- predictable system behavior
- minimal complexity
- secure content unlocking
- clear lifecycle management

Each decision includes reasoning and rejected alternatives.

---

# ADR-001: Link Lifecycle States

## Decision

Links will use the following lifecycle states:

draft
active
suspended
deleted

Database enum:

links.status

---

## State Definitions

### Draft

Link created but not published.

Conditions:

seller has not connected Stripe
OR
seller has not clicked publish

Draft links are private.

---

### Active

Link is publicly accessible and can receive payments.

Requirements:

stripe_account_id present
price >= minimum
valid destination_url

---

### Suspended

Link disabled by platform moderation.

Possible reasons:

- abuse reports
- malware links
- copyright violations

Suspended links return:

Product unavailable

---

### Deleted

Seller removed the product.

However:

existing purchases must remain valid

Purchased buyers must still access the resource.

---

## Why Links Do NOT Have "Purchased" State

"Purchased" is not a property of a link.

It is a property of a **transaction between a buyer and a link**.

Correct data model:

Link
↓
Purchase
↓
Buyer

Example:

Link A
├── Purchase #1 (buyer1@email)
├── Purchase #2 (buyer2@email)
├── Purchase #3 (buyer3@email)

Therefore purchase state belongs in:

purchases table

Not the link entity.

# ADR-002: Purchase Lifecycle

Purchases represent completed payments.

Purchase table:

purchases

Fields:

id
link_id
buyer_email
stripe_payment_id
amount
created_at

Optional fields:

email_verified
unlock_token_hash

Purchases never expire by default.

Buyers should retain permanent access unless the seller violates policies.

# ADR-003: Expiring Links (Future Feature)

The MVP does NOT include time-limited links.

However the architecture allows it.

Possible future field:

links.expires_at

Example:

expires_at = 2025-12-01

Expired behavior:

status = expired

Response:

This product is no longer available

Purchased buyers should still retain access.

# ADR-004: Unlock Token Security

Content access will use **single-use signed tokens**.

Unlock URL:

/unlock?token=abc123

Token properties:

random 32 byte value
stored as hash
single-use
expires in 24 hours

Flow:

payment success
↓
create unlock token
↓
send email with link
↓
token validated
↓
redirect to destination URL

This prevents unlimited sharing of unlock links.

# ADR-005: Slug URL Strategy

Public product URLs use slugs.

Example:

/pay/notion-crm-a3f2

Slug generation:

slugify(title) + "-" + crypto.randomBytes(2).toString("hex")  → 4-char random hex suffix

Examples: notion-crm-a3f2 · figma-ui-kit-d91c · brand-files-4e7b

Rationale for random suffix:
- Global uniqueness without sequential counters (no information leakage about # of products)
- Collision probability: 1/65536 per base slug — negligible, retry loop handles it (max 5 attempts)
- Slugs remain human-readable: base title is preserved
- Sellers do not edit slugs in MVP

Database constraint:

UNIQUE(slug)  — global, not per-seller

Slug lookups always filter WHERE status = 'active'.
Draft, suspended, and deleted links are never served from /pay/[slug].

Sellers do not manually edit slugs in MVP.

# ADR-006: Minimum Product Price

Minimum price:

$9.99

Reason:

Stripe payment fees make very small products unprofitable.

Example:

$1 product
Stripe fee ≈ $0.33
Platform fee ≈ $0.045
Seller receives ≈ $0.62

Minimum price prevents seller loss.

# ADR-007: Free Tier Abuse Protection

To prevent spam and database abuse:

Limits per user:

max_links_per_user = 20
max_links_per_day = 5

API rate limit:

10 requests per minute

These limits are sufficient for MVP.

# ADR-008: Buyer Re-Access

Buyers use the same Supabase OTP auth as sellers — no separate account system.

After purchase, the buyer verifies their email on the success page (6-digit OTP).
This creates a Supabase session scoped to their email. From that point forward:

Primary path (session-based):

buyer visits /orders
↓
middleware checks session → redirect to /auth if none
↓
OTP sign-in → session created
↓
fetch purchases WHERE buyer_email = user.email AND status = 'paid'
↓
visit /orders/[id] → click "Access content" → server redirect to delivery_url

Delivery URL is NEVER rendered in HTML — only accessible server-side after auth check.

Fallback path (sessionless — for re-access via email):

buyer clicks link in unlock email: /unlock?token=xxx
↓
server validates token
↓
shows confirmation screen (token NOT consumed on GET — prevents email scanner burns)
↓
buyer clicks "Access content →" → Server Action consumes token → redirect to delivery_url

Query (orders page):

SELECT * FROM purchases WHERE buyer_email = user.email AND status = 'paid'

# ADR-009: Webhook Idempotency

Stripe webhooks may be delivered multiple times.

Solution:

Unique constraint:

purchases.stripe_payment_id UNIQUE

Webhook logic:

if payment_id exists
ignore
else
create purchase

This prevents duplicate purchases.

# ADR-010: Seller Earnings Transparency

Seller dashboard must display revenue breakdown.

Example transaction:

Product price: $20
Platform fee (4.5%): $0.90
Stripe fee: $0.88
Net earnings: $18.22

Dashboard totals:

total revenue
total platform fees
stripe fees
net payout

Transparency increases seller trust.

# Core Architecture Principle

The system remains intentionally simple.

The platform does NOT host content.

The platform only controls:

payments
access gating
unlock verification

Core workflow:

Create link
↓
Pay
↓
Unlock




⸻

Answer to Your Expiry Question

Yes — links could have expiration, but it’s better as a future feature, not MVP.

Why:

Most digital products:
	•	templates
	•	prompt packs
	•	datasets

are expected to provide permanent access.

Expiration makes more sense later for:

courses
subscriptions
community access
time-limited reports

So the correct design is:

MVP:
no expiration

Future:
links.expires_at
